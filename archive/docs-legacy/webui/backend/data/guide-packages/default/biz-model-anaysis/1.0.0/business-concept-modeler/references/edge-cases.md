# 边界情况处理（Edge Cases）

当领域识别置信度为"低"，或出现以下特殊情况时，读取本文件。

---

## 情况一：置信度低 / 信号模糊

**触发条件**：STEP 1 判断置信度为"低"，或无法确定一级域。

**处理方式：多域模式**

1. 列出所有可能的领域（≤3个），按可能性排序
2. 为每个候选领域分别执行 STEP 2 搜索（每个域1-2条查询）
3. 在 STEP 3 中合并所有领域的框架，标注每个实体的来源域
4. 在输出的"抽取说明"章节中：
   - 注明"本文档跨越多个业务领域"
   - 列出每个域的实体子集
   - 标注哪些实体是跨域共享的

---

## 情况二：跨领域复合文档

**触发条件**：文档明确包含多个业务模块（如"采购+财务"的综合合规手册）。

**处理方式**：

1. 按文档章节划分域边界
2. 为每个章节/模块单独识别领域
3. 在实体清单中增加"所属模块"列
4. ER 图中用注释标注模块边界：
   ```mermaid
   %% ===== 采购模块 =====
   合同 ||--o{ 付款申请 : "发起"
   %% ===== 财务模块 =====
   付款申请 }o--|| 资金计划 : "归属"
   ```

---

## 情况三：文档极短 / 信息不足

**触发条件**：文档少于500字，或仅包含流程图/表格而无文字说明。

**处理方式**：

1. 从有限信号中尽量提取
2. 在输出中明确标注每个实体的"证据强度"：
   - ★★★ 有明确定义和属性描述
   - ★★☆ 多次出现但无详细属性
   - ★☆☆ 仅出现一次，推断存在
3. 搜索时增加查询："[领域] 标准业务实体 完整列表"以补充缺失信息
4. 在"建议补充信息"中明确列出需要用户补充的内容

---

## 情况四：技术文档（非业务文档）

**触发条件**：文档是数据库设计文档、API 接口文档、技术架构文档。

**处理方式**：

1. 从技术实体反向推导业务实体
2. 忽略纯技术字段（created_at, updated_by, version 等）
3. 将数据表名映射为业务实体名（去掉技术前缀/后缀）
4. 搜索时增加："[系统名称] 业务背景" 以理解技术实现背后的业务语义
5. 在输出说明中注明："本模型基于技术文档反向推导，建议与业务方确认"

---

## 情况五：文档含大量数字/金额规则

**触发条件**：文档中有超过5条涉及具体金额/数量的规定。

**处理方式**：

1. 在业务规则清单中单独增加"数值规则"章节
2. 提取规则时保留原始数值（不做推断或概括）
3. 标注规则的适用条件（如"适用于合同金额超过100万的情况"）

---

## 搜索失败处理

**触发条件**：搜索返回结果与领域不相关，或搜索工具不可用。

**降级处理**：

1. 仅使用基础层（base-layer.md）执行抽取
2. 在输出中明确注明："本次抽取未使用领域参考框架，仅基于通用规则"
3. 降低对领域标准术语的依赖，完全以文档原文术语为准
4. 建议用户提供补充参考文档
